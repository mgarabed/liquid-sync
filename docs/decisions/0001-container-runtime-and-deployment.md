# 0001 — Container runtime and deployment model

Status: accepted
Date: 2026-11-22
Work item: `work/0006-decide-docker-vs-podman-for-local-development-ad`

## Context

liquid-sync's reference production host is a Raspberry Pi 4 running
[Fedora IoT](https://docs.fedoraproject.org/en-US/iot/), an image-based OS
that runs workloads as containers under Podman and systemd. The owner's Pi is
an 8 GB Pi 4 that boots from a USB flash drive, and it's shared with other
homelab services, which live in a separate private repo. The dev machine is
a Mac that already runs Colima with Docker for other projects. CLAUDE.md
requires `compose.yaml` to work with both `docker compose` and
`podman compose`. Amended 2026-11-26 (0010): corrected the Pi's memory and
boot drive.

On Fedora IoT, the native way to run containers under systemd is
[Quadlet](https://docs.podman.io/en/stable/markdown/podman-systemd.unit.5.html):
`.container`, `.pod` and `.volume` files that a systemd generator turns into
services. [`podman auto-update`](https://docs.podman.io/en/stable/markdown/podman-auto-update.1.html)
only works for containers that "run inside a systemd unit", and it restarts
that unit after pulling a new image. So we need one container definition that
compose can run on a laptop and that becomes one systemd unit per container on
the Pi.

## Options

Where the container definitions are kept (the source of truth):

- **A. `compose.yaml` as source, quadlets generated by
  [podlet](https://github.com/containers/podlet).**
  - Costs: one more tool, plus a restricted compose dialect. Podlet rejects
    `${VAR}` interpolation, `include`, `extends`, `build`, `deploy`,
    `profiles` and `scale` (all tested, see Evidence).
  - Gives up: the compose features in that list, and ownership of the
    conversion logic, which belongs to an upstream project.
- **B. `compose.yaml` run under one systemd unit** (`podman compose up` as a
  service).
  - Costs: a compose implementation layered onto Fedora IoT.
  - Gives up: `podman auto-update`, which needs each container in its own
    systemd unit. It also gives up per-container restart, logs and dependency
    ordering in systemd.
- **C. Hand-written quadlets plus a hand-written `compose.yaml`.**
  - Costs: two copies of every container definition, kept in sync by
    discipline alone.
  - Gives up: any guarantee that what is tested locally is what runs on the
    Pi. The two copies drift silently.

## Decision

- **Production OS:** Fedora IoT on the Pi 4, booting from a USB flash drive
  (amended 2026-11-26, 0010). Any Fedora IoT host works; nothing in `deploy/`
  is specific to the Pi.
- **Rootless:** liquid-sync runs rootless, as a dedicated service user (no
  login shell, no sudo, no SSH keys) with lingering enabled ([`loginctl enable-linger`](https://www.freedesktop.org/software/systemd/man/latest/loginctl.html)),
  so its units start at boot without a login session. The quadlets go in that
  user's own rootless unit path, `~/.config/containers/systemd/`
  ([podman-systemd.unit(5)](https://docs.podman.io/en/stable/markdown/podman-systemd.unit.5.html)).
  Quadlet resolves relative `EnvironmentFile=` and bind-mount paths against
  the unit file's directory, so the env file (mode 0600) and config
  directories are installed next to the quadlets, in a directory the service
  user owns. `deploy/` can then install and update them without root.
  Nothing in liquid-sync needs root. Rootless Podman can't bind ports below
  1024 ([rootless.md](https://github.com/containers/podman/blob/main/rootless.md)),
  and liquid-sync doesn't need to: the host's own tailscaled serves 443 (see
  Tailscale publishing). Amended 2026-11-26 (0010): the Tailscale sidecar
  that ran in userspace networking is dropped.
- **Shared host and the homelab-repo split:** the Pi is shared with other
  homelab services. This repo owns only the liquid-sync stack: its quadlets,
  its service user, and its data covered by `backup`/`restore`. The host OS
  setup and the other services live in a separate private repo. Other
  services may run rootful; that's their repo's business.
- **Source of truth:** option A. `compose.yaml` is the source. The quadlets
  in `deploy/` are generated by `podlet compose` (without `--pod`, see the
  compose rules), committed, and reviewed in PRs.
- **Local runtime:** on the dev Mac, liquid-sync uses
  [Podman machine](https://docs.podman.io/en/stable/markdown/podman-machine-init.1.html)
  and `podman` commands, alongside Colima. Rootless matches production. The
  evidence below was gathered on a rootful machine. The rootless dry-run
  validates unit generation only; rootless runtime is first exercised in
  0002. Other contributors and CI may use `docker compose`.
- **Colima coexistence:** see the Local development rules below. Colima stays
  the default engine for `docker`.
- **Podman compatibility:** proven by a `sdlc verify` step that 0002 adds once
  `compose.yaml` exists. It regenerates the quadlets with podlet, fails on
  any difference from the committed ones, and dry-runs them with
  `quadlet -dryrun -user`, all in containers pinned by digest (the commands
  are in Evidence). The tooling digests are fixed; only runtime images
  float within their pinned tag, for `podman auto-update`. A real run on the Pi happens in the Phase 5 deployment item.
  Amended 2026-11-24 (0008): the step is added by 0008, not 0002. It runs
  `scripts/check-quadlets --skip-if-no-podman`, which exits 0 with a SKIPPED
  warning only when no podman binary is found or it can't reach an engine;
  any other failure fails verify.
- **Compose rules:** the checklist below. 0002 applies it line by line, and
  so does every later change to `compose.yaml`.
- **Tailscale publishing:** amended 2026-11-26 after homelab ADR 0005, which
  drops the Tailscale sidecar. liquid-sync is published as the Tailscale
  Service `svc:liquid-sync` at `https://liquid-sync.<tailnet>.ts.net` on 443.
  The host's own `tailscale serve` terminates TLS and forwards to
  `127.0.0.1:5984`. The homelab repo owns publishing: which `tag:server`
  hosts advertise the Service, the serve config, and the tailnet policy. The
  stack runs no Tailscale container, and the liquid-sync service user never
  controls tailscaled. A Mac signed in as a user can't host a Service, so
  local development stays on localhost.
- **Memory budget:** 1 GB for all liquid-sync containers together, set per
  service with `mem_limit:`, which podlet maps to quadlet `Memory=`. If Spike A
  (0007) picks the headless-Obsidian archiver, it must show the archiver fits
  within this budget, or reopen this ADR.

### Compose rules

- [ ] Fully qualified image names (`docker.io/library/couchdb`, not `couchdb`).
- [ ] Tags pinned to a minor version with amd64 and arm64 manifests
      (`couchdb:3.5`); never `latest`. `podman auto-update` follows the
      pinned tag, so patch releases arrive and minor upgrades are a commit.
- [ ] Every service sets `labels: io.containers.autoupdate: registry`, which
      podlet maps to `AutoUpdate=registry`. Without it auto-update skips the
      container.
- [ ] Every service sets `container_name:` and joins one named network
      declared under `networks:`. Services address each other only by
      `container_name`. Podlet maps these to `ContainerName=` and a
      `.network` unit; the bare service name doesn't resolve once quadlet
      runs the containers. `ports:` apply per container. A service that
      needs another's network namespace (`network_mode: service:x`) isn't
      covered here: 0002 tests that podlet maps it before using it.
- [ ] `:Z` on every bind mount (`./conf:/conf:ro,Z`), for SELinux on Fedora.
      `:Z` relabels the host directory, so bind-mount only directories
      liquid-sync owns, never `$HOME`, `/etc` or another shared path.
      `docker compose` on Colima accepts `:Z` too (tested).
- [ ] `env_file:` for configuration and secrets; no `${VAR}` interpolation
      anywhere in the file.
- [ ] `env_file:` and bind-mount sources are relative paths inside the
      directory `deploy/` installs next to the quadlets, never absolute
      host paths.
- [ ] None of `include`, `extends`, `build`, `deploy`, `profiles` or `scale`.
      Podlet rejects them all.
- [ ] Memory limits via `mem_limit:` (not `deploy.resources`), summing to
      1 GB or less.
- [ ] Host ports bind to loopback only (`127.0.0.1:<port>:<port>`), and only
      ports at 1024 or above.
- [ ] A top-level `name:`, so the compose project name is stable.
- [ ] No Tailscale container, auth key or state volume. CouchDB binds to
      `127.0.0.1` only, and the tailnet reaches it only through the host's
      `tailscale serve` on `svc:liquid-sync`, never `tailscale funnel`. The
      tailnet policy in the homelab repo limits access to 443 on
      `svc:liquid-sync` (homelab ADR 0005). CouchDB keeps
      `require_valid_user` on regardless, because the loopback port is
      reachable by other local users on a shared host. Amended 2026-11-26.

### Local development

These rules keep the dev Mac's Colima setup untouched:

- Docs and scripts for local development use `podman` commands, never `docker`.
- `podman-mac-helper` must not be active. The official `.pkg` installer sets it
  up, and once the machine starts it links `/var/run/docker.sock` to Podman
  (observed during this work; see also
  [Podman Desktop: podman-mac-helper](https://podman-desktop.io/docs/migrating-from-docker/using-podman-mac-helper)).
  If it's present, remove it with `sudo /opt/podman/bin/podman-mac-helper uninstall`.
  Leave Podman Desktop's Docker compatibility setting off.
- Don't change Docker contexts or `DOCKER_HOST`. `docker context show` stays
  `colima`.
- Host ports bind to 127.0.0.1 only, and are checked with
  `lsof -nP -iTCP:<port> -sTCP:LISTEN` against ports already in use before
  they're chosen.
- `podman compose` is a thin wrapper that runs `docker-compose` when it's
  installed, pointed at the Podman socket
  ([podman-compose(1)](https://docs.podman.io/en/stable/markdown/podman-compose.1.html)).
  The Evidence below shows the containers land in Podman. To pin the provider
  anyway, set `PODMAN_COMPOSE_PROVIDER` or `compose_providers` in
  [containers.conf(5)](https://github.com/containers/common/blob/main/docs/containers.conf.5.md).

### Why podlet

Podlet converts compose files and `podman` commands into Quadlet files. It
lives in the `containers` GitHub organisation alongside Podman, is
[MPL-2.0](https://github.com/containers/podlet/blob/main/LICENSE) licensed,
and publishes multi-arch images at
[ghcr.io/containers/podlet](https://github.com/containers/podlet/pkgs/container/podlet).
We only ever run it from that image, pinned by digest, so nothing gets
installed on any host. Its [releases](https://github.com/containers/podlet/releases)
are slow: v0.3.0 shipped in May 2024, then v0.3.1 in February 2026 and v0.3.2
in May 2026. Its README cautions that it "is not meant to be an end-all
solution for creating and maintaining Quadlet files" and that generated files
"should always be reviewed". So we commit the generated quadlets, review them
in PRs, and check them with the verify step. If podlet is abandoned or breaks,
the committed quadlets stay valid and become hand-maintained. That's option C,
with the verify step's diff check removed.

### Evidence

Gathered on 2026-11-22 on the dev Mac. Podman 6.1.4 ran in a rootful libkrun
machine, with Colima running alongside. The sample is a throwaway file, not
committed:

```yaml
name: lssample
services:
  couchdb:
    image: docker.io/library/couchdb:3.5
    env_file: couchdb-vars.txt        # fake values
    ports: ["127.0.0.1:15984:5984"]
    volumes: [couchdb-data:/opt/couchdb/data]
    mem_limit: 512m
  sidecar:
    image: docker.io/library/alpine:3.24
    command: ["sleep", "infinity"]
    volumes: ["./conf:/conf:ro,Z"]
    mem_limit: 32m
volumes:
  couchdb-data:
```

Local run, checking which engine the containers land in:

```console
$ podman compose up -d                                  # exit 0
$ podman ps --filter label=com.docker.compose.project=lssample --format '{{.Names}} {{.Image}}'
lssample-couchdb-1 docker.io/library/couchdb:3.5
lssample-sidecar-1 docker.io/library/alpine:3.24
$ docker ps -q --filter label=com.docker.compose.project=lssample | wc -l
0
$ docker context show
colima
$ podman compose down -v                                # exit 0
```

Image digests (multi-arch index) for the verify step to pin:

- `ghcr.io/containers/podlet:v0.3.2@sha256:90cb8214ade9da09b5a8fd93da20f9bfcad5c3ae40093c95c31be8dce29fd22e`
- `quay.io/podman/stable:v6.1.3@sha256:1d280cfab8e4cdaa221229c121f681c67463fbd82ad2fa6d13fdcf91c6fc747e`

Conversion with podlet (`ghcr.io/containers/podlet:v0.3.2`):

```console
$ podman run --rm -v "$SAMPLE":/w:Z -w /w ghcr.io/containers/podlet:v0.3.2 --file out compose --pod compose.yaml
Wrote to file: out/lssample-couchdb.container
Wrote to file: out/lssample-sidecar.container
Wrote to file: out/lssample.pod
# exit 0
```

The output maps `env_file:` to `EnvironmentFile=`, `mem_limit:` to
`Memory=`, and the published port to `PublishPort=` on the `.pod`. A
named volume with no options needs no `.volume` file.

Validation with Podman's quadlet generator (`quay.io/podman/stable:v6.1.3`):

```console
$ podman run --rm -v "$SAMPLE/out":/q:Z -e QUADLET_UNIT_DIRS=/q quay.io/podman/stable:v6.1.3 /usr/libexec/podman/quadlet -dryrun
---lssample-couchdb.service---
---lssample-sidecar.service---
---lssample-pod.service---
# exit 0; stderr only "Loading source unit file" lines
$ podman run --rm -v "$SAMPLE/out":/q:Z -e QUADLET_UNIT_DIRS=/q quay.io/podman/stable:v6.1.3 /usr/libexec/podman/quadlet -dryrun -user
# rootless: same three units, exit 0
$ podman run --rm -v "$BAD":/q:Z -e QUADLET_UNIT_DIRS=/q quay.io/podman/stable:v6.1.3 /usr/libexec/podman/quadlet -dryrun
# $BAD holds one .container with an unknown key
quadlet-generator[1]: converting "broken.container": unsupported key 'NotAQuadletKey' in group 'Container' ...
# exit 1 (negative control: the dry-run really validates)
```

Service addressing and auto-update, checked after review. The sample above
uses `--pod`. Inside a pod, Quadlet names each container `systemd-<unit>`,
and the bare service name didn't resolve:

```console
$ podman run --rm --pod <pod> docker.io/library/alpine:3.24 getent hosts couchdb
# no result; /etc/hosts lists only systemd-lssample-couchdb
```

So `--pod` is dropped. A second sample gives each service `container_name:`,
joins one named network, and sets `io.containers.autoupdate: registry`. For
the compose run, the `couchdb` service ran `alpine:3.24` with `sleep infinity`,
because CouchDB exits at start without an admin set:

```yaml
name: lsnet
services:
  couchdb:
    image: docker.io/library/couchdb:3.5
    container_name: lsnet-couchdb
    networks: [lsnet]
    labels:
      io.containers.autoupdate: registry
  probe:
    image: docker.io/library/alpine:3.24
    container_name: lsnet-probe
    command: ["sleep", "infinity"]
    networks: [lsnet]
    labels:
      io.containers.autoupdate: registry
networks:
  lsnet:
```

```console
$ podman run --rm -v "$NET":/w:Z -w /w ghcr.io/containers/podlet:v0.3.2 --file out compose compose.yaml
Wrote to file: out/couchdb.container      # ContainerName=lsnet-couchdb, AutoUpdate=registry
Wrote to file: out/probe.container        # Network=lsnet.network
Wrote to file: out/lsnet.network
# exit 0
$ podman run --rm -v "$NET/out":/q:Z -e QUADLET_UNIT_DIRS=/q quay.io/podman/stable:v6.1.3 /usr/libexec/podman/quadlet -dryrun -user
---lsnet-network.service---
---couchdb.service---
---probe.service---
# exit 0
$ podman network create systemd-lsnet
$ podman run -d --rm --name lsnet-couchdb --network systemd-lsnet docker.io/library/alpine:3.24 sleep 60
$ podman run --rm --network systemd-lsnet docker.io/library/alpine:3.24 getent hosts lsnet-couchdb
<ip>       lsnet-couchdb.dns.podman lsnet-couchdb
$ podman compose up -d && podman exec lsnet-probe getent hosts lsnet-couchdb
<ip>       lsnet-couchdb.dns.podman lsnet-couchdb
```

The name resolves in both setups, and the generated `podman run` lines carry
`--label io.containers.autoupdate=registry`.

Negative checks for the compose rules: podlet v0.3.2 exits 1 on a compose
file using `${TAG}` (even with `TAG` set), `include`, `extends`, `build`,
`deploy`, `profiles` or `scale`.

## Consequences

- liquid-sync on a host needs a dedicated user with lingering, and its
  quadlets, env file (0600) and config installed together in that user's
  `~/.config/containers/systemd/`, all declared in `deploy/`.
  `podman auto-update` runs as that user's `podman-auto-update.timer`.
- The stack needs no Tailscale container and no added capabilities. The
  host's tailscaled publishes `svc:liquid-sync` (homelab ADR 0005), so the
  earlier open question, whether `tailscale serve` works in a rootless
  userspace sidecar, no longer applies. Amended 2026-11-26.
- 0002 writes `compose.yaml` to the compose rules and the check script
  (regenerate, diff, `quadlet -dryrun -user`); 0008 adds the verify step that
  runs it, skipping with a warning when Podman is unavailable.
- Spike A (0007) must fit the archiver in the 1 GB budget or reopen this ADR.
- The Phase 2 CLI uses `podman` commands for local development.
- A wrong decision here is superseded by a new ADR, not edited.
