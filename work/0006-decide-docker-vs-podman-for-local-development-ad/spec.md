# Spec: Choose the container runtime and deployment model (ADR 0001)

## Areas of concern
- [ ] **The rootful rationale was partly wrong.** In discussion I said a monitoring agent needs rootful Podman for full container visibility. Datadog's docs say otherwise: the agent supports rootless Podman by reading the Podman database, and rootful Podman adds the Docker-compatible socket (so it emits `docker.*` metrics) ([Datadog: Podman support](https://docs.datadoghq.com/containers/guide/podman-support-with-docker-integration/)). That leaves two reasons for rootful: Pi-hole binding port 53, which is the homelab's concern, not liquid-sync's; and the Tailscale sidecar's `/dev/net/tun` and `NET_ADMIN` needs, which is liquid-sync's own. — Proposed resolution: keep rootful as the supported deployment, state the corrected reasons, and record rootless as untested rather than unsupported.
- [ ] **The container-definition source of truth can't be decided by convention alone.** Each option costs something:
  - (A) `compose.yaml` plus quadlets generated by [podlet](https://github.com/containers/podlet) adds a tool. Podlet doesn't support compose `${VAR}` interpolation, `include`, `build`, `deploy`, `profiles` or `extends`.
  - (B) Running compose under one systemd unit loses `podman auto-update`, which needs each container to run in its own systemd unit ([podman-auto-update(1)](https://docs.podman.io/en/v4.6.1/markdown/podman-auto-update.1.html)). It also needs a compose implementation layered onto Fedora IoT.
  - (C) Hand-written quadlets plus a hand-written `compose.yaml` means two copies that can drift.

  Proposed resolution: (A), with podlet run from its published container image (nothing installed on any host), `compose.yaml` restricted to features podlet maps (`env_file:` instead of `${VAR}` interpolation), and a check that regenerates the quadlets and fails on any difference. The ADR justifies podlet, as CLAUDE.md requires for a new tool.
- [ ] **The Pi 4 has no hardware clock.** At boot its time is wrong until NTP syncs, and NTP needs DNS. A greenboot health check that depends on correct time (TLS validity, DNSSEC) can fail and roll back good updates; [this happened on Fedora IoT before](https://bugzilla.redhat.com/show_bug.cgi?id=2042665). If the host also sends its own DNS to the Pi-hole container, there's a chicken-and-egg problem at boot. — Proposed resolution: the ADR lists two consequences. liquid-sync's own health checks must not depend on wall-clock time at boot. The host should use upstream DNS for itself, not its own Pi-hole; that part is guidance for the homelab repo.
- [x] Dependencies: none. This item only writes docs. 0002 already depends on it (`sdlc dep 0002`). History: rejected item 0001 had planned a Linux container check; there's no other prior work on these files.

## Design
- **New file:** `docs/decisions/0001-container-runtime-and-deployment.md`. This is the first ADR and sets the format for later ones (`# NNNN — title`, status, date, then the four sections). About a page and a half, with links to sources inline.
- **Edited file:** `docs/project-plan.md`, changed only in the places listed in R9. No other rewording.
- **Evidence for R8 (option A only).** The build runs these on the dev machine through Docker (Colima), so nothing gets installed:
  - podlet's published container image (the image name and tag come from podlet's README at build time; not verified here), run as `docker run --rm -v "$PWD/<tmp>":/w -w /w <podlet image> compose --pod compose.yaml` on a throwaway compose file in the scratchpad
  - the output then goes through Podman's quadlet generator in dry-run mode, inside `quay.io/podman/stable`

  The exact image tags are pinned and recorded in the ADR. If an image or the dry-run path doesn't work as expected, the build stops and reports back rather than picking another option itself.
- **No code, compose or quadlet files** are added to the repo by this item.
- **Rollback:** revert the merge. An ADR that later proves wrong is superseded by a new ADR, not edited.

## Open questions
- [ ] Local runtime: stay on Colima with Docker, or move to `podman machine`? — Proposed: Colima. On macOS, `podman machine` doesn't reproduce the Pi's SELinux or systemd anyway, and with option A the Pi-specific check is the quadlet dry-run, not the local runtime.
- [ ] How is Podman compatibility proven before work counts as done? — Proposed: a verify step (added by 0002 once `compose.yaml` exists) that regenerates the quadlets with podlet, fails on any difference from the committed quadlets, and dry-runs them with Podman's quadlet generator, all in containers. A real run on the Pi happens in the Phase 5 deployment item.
- [ ] What memory budget should liquid-sync target on a shared 4 GB Pi? — Proposed: 1 GB for all liquid-sync containers together, set as compose and quadlet memory limits. If Spike A (0007) picks the headless-Obsidian archiver, it has to show it fits, or come back to this ADR.
- [x] Source of truth: generated quadlets, compose under one unit, or quadlets as source? — answer: see the second area of concern (proposed A).
